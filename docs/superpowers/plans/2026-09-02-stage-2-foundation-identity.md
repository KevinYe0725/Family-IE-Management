# Stage 2 Foundation and Identity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Introduce safe Flyway migrations and replace the single-user household model with email registration, household memberships, invitations, and role authorization without losing Stage 1 data.

**Architecture:** Flyway establishes the Stage 1 baseline and applies identity/membership changes before Hibernate validates the schema. Spring Security authenticates by normalized email while a compatibility alias keeps the demo username working; a centralized membership permission service resolves household and role for all later modules.

**Tech Stack:** Java 17, Spring Boot 4.1.1, Spring Security, Spring Data JPA, Flyway Core, H2, JUnit 5, MockMvc.

**Spec:** `docs/superpowers/specs/2026-09-02-family-finance-stage-2-design.md`

## Global Constraints

- Existing Stage 1 file databases must migrate in place only after a timestamped backup is created by the startup flow.
- Fresh databases run `V1__stage1_schema.sql`; existing nonempty databases baseline at version 1 and then run V2.
- Emails are trimmed, lower-cased, and globally unique; passwords are 8–72 characters and BCrypt encoded.
- Invite plaintext is returned once and never persisted; only a SHA-256 hash is stored.
- Household authorization is based on `FamilyUserPrincipal.userId` plus an active membership.
- `OWNER`, `ADMIN`, and `MEMBER` permissions match the approved spec exactly.
- Stage 1 `/api/auth/login`, `/api/session`, and demo credentials remain compatible throughout this plan.

## Plan API Contracts

- `POST /api/auth/register`
- `POST /api/auth/change-password`
- `GET|PATCH|DELETE /api/family`
- `GET|POST|DELETE /api/family/invites`
- `GET|PATCH /api/family/memberships`
- `POST /api/family/transfer-ownership`

- [ ] **Step 3: Add Flyway and exact SQL migrations**

Add `org.flywaydb:flyway-core` and `org.flywaydb:flyway-database-h2`. V1 recreates the current entity schema including indexes/constraints. V2:

```sql
alter table app_users add column email varchar(254);
alter table app_users add column display_name varchar(40);
alter table app_users add column status varchar(16) default 'ACTIVE' not null;
alter table households add column status varchar(16) default 'ACTIVE' not null;
alter table households add column archived_at timestamp with time zone;
update app_users set email='demo@local.family', display_name='演示用户' where username='demo';
alter table app_users alter column email set not null;
create unique index uk_app_users_email on app_users(email);

create table household_memberships (
  id bigint generated by default as identity primary key,
  household_id bigint not null,
  user_id bigint not null,
  role varchar(16) not null,
  status varchar(16) not null,
  joined_at timestamp with time zone not null,
  constraint uk_membership_household_user unique(household_id, user_id),
  constraint fk_membership_household foreign key(household_id) references households(id),
  constraint fk_membership_user foreign key(user_id) references app_users(id)
);
```

V2 also adds `family_members.linked_user_id`, inserts the demo owner membership, links the demo member, and creates `family_invites` with token hash, expiry/use count/revocation fields.

- [ ] **Step 3: Implement invite locking and JOIN registration**

- [ ] **Step 4: Implement permission matrix and ownership transfer**

`FamilyPermissionService` exposes explicit methods such as `requireAdmin`, `requireOwner`, `canMutateTransaction(context, createdBy)`, and `canConfirmAssignedOccurrence(context, assignee)`. Ownership transfer locks both memberships and atomically swaps roles; a family must always have exactly one owner.

Family archive requires the owner to submit the exact current family name, locks the household/memberships, sets household `ARCHIVED`, revokes invites, deactivates memberships, and invalidates the current session after commit. No domain row is physically deleted.
