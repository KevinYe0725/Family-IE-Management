# Family Finance MySQL Server Runtime Design

## Status

Proposed for implementation after user approval.

## Goal

Make MySQL 8 the only production runtime database and run the Family Finance Spring Boot application on the Ubuntu 22.04 server. Local H2 execution is no longer a product requirement; H2 remains test-only so the existing isolated test suite can run during the server build.

## Current evidence

- The application currently defaults to file-mode H2 in `src/main/resources/application.yml`.
- Flyway V1–V12 contain H2-oriented syntax, including identity columns, `timestamp with time zone`, and generated columns.
- The test suite contains many `@SpringBootTest` classes without an explicit profile, while `src/test/resources/application-test.yml` already defines an isolated H2 database.
- The server is Ubuntu 22.04.5 LTS and currently has Git but no Java, MySQL, or Docker.
- The server repository checkout is `/root/Family-IE-Management` on `codex/family-finance-stage-2` at commit `111d340`.

## Architecture

### Production runtime

1. `spring.datasource` defaults to MySQL 8 using environment-backed values (`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, and `SPRING_DATASOURCE_PASSWORD`).
2. Flyway uses `classpath:db/migration/mysql`, whose V1–V12 scripts are MySQL-compatible equivalents of the current schema history.
3. The application uses MySQL Connector/J and Flyway's MySQL database module. JPA remains `ddl-auto=validate`; Hibernate does not create or mutate the schema.
4. MySQL listens locally on the server. The application is managed by systemd and stores no database credential in source control, logs, or the repository.

### Test runtime

1. H2 remains a test-scoped dependency.
2. Maven Surefire activates the `test` Spring profile for all Spring tests, ensuring tests use the existing in-memory H2 configuration even when a test class omits `@ActiveProfiles("test")`.
3. Existing migration fixtures that explicitly use `classpath:db/migration` continue to validate the H2 migration history; a separate real-server smoke check validates the MySQL migration history.

### Server deployment

1. Install OpenJDK 17 and MySQL 8 from Ubuntu packages.
2. Create a fresh `family_finance` database and a least-privilege local application account. The server generates the password locally; it is written only to a root-readable systemd environment file.
3. Build the checked-out commit with the Maven Wrapper.
4. Run the packaged JAR as a dedicated service user from a fixed working directory so all relative paths are stable.
5. Use `systemctl` and `journalctl` for lifecycle and logs. Keep the application bound to `127.0.0.1`; use an SSH tunnel for private access until a reverse proxy/domain is explicitly requested.

## Migration conversion rules

- `generated by default as identity` becomes MySQL `bigint auto_increment`.
- `timestamp with time zone` becomes `datetime(6)` so Java `Instant` values retain microsecond precision under MySQL/Hibernate.
- Generated columns are expressed with MySQL's typed `generated always as (...) stored` form.
- Existing constraints, indexes, unique keys, foreign keys, and check expressions are preserved unless MySQL requires an equivalent syntax.
- Migration versions remain V1 through V12 so Flyway history is easy to inspect on the fresh database.

## Data and cutover boundary

The server currently has no application database. The first MySQL startup initializes a fresh schema and demo data; this change does not attempt to import the previous local H2 files. If H2 data migration is later required, it will be treated as a separate, explicitly tested project.

## Acceptance criteria

1. `./mvnw package` passes on the server with tests using H2 and the production configuration compiling with MySQL Connector/J.
2. MySQL starts, Flyway reaches V12 without validation or migration errors, and the application health endpoint returns HTTP 200.
3. A new user registration creates a user, household, membership, default account, and defaults in MySQL.
4. After a complete service restart, the new account can log in and its household data remains available.
5. `git status` is clean; no password, token, generated database file, or environment file is committed.

## Risks and mitigations

- MySQL rejects H2-only DDL: maintain a separate MySQL migration location and run it against the real server before declaring success.
- Tests accidentally connect to production defaults: force the `test` profile from Surefire and keep all test database values in test resources.
- Relative paths or credentials vary under systemd: set `WorkingDirectory`, `EnvironmentFile`, and restrictive file permissions in the service unit.
- A server-side GitHub outage blocks updates: retain the GitHub origin and use the existing SSH bundle transfer only as a fallback.
