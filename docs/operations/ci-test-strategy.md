# CI 按需测试与发布策略

## 发布前做什么

1. `plan`：验证选测规则及发布安全脚本，判断本次所有未验证改动，输出测试清单。
2. `frontend-build` 与 `frontend-tests` 同时开始。构建检查 TypeScript 并生成带当前提交标识的静态资源；测试运行核心用例及关联模块。
3. `build` 在前端静态资源就绪后开始，不等待前端测试结束。下载同一次运行的前端产物，执行后端选定测试并打包；不会再次安装 Node 或构建前端。
4. `checks` 汇总所有结果：缺失、失败或取消的必需检查都阻止发布。只有明确的文档/无变化场景允许应用任务跳过。
5. `deploy` 继续使用现有校验和、最新提交保护、SSH 主机验证、服务器恢复机制和公网版本/健康检查。

`main` 和 Stage 2 的推送/PR 都会检查。**main 普通推送不部署**；Stage 2 代码推送仍自动部署。PR、夜间检查、纯文档改动均不部署。main 手动部署仍须明确勾选 `deploy_main`。

## 什么测试可以不跑

| 改动范围 | 执行范围 |
| --- | --- |
| README、许可文件、docs 下明确识别的文档/图片 | 选测及发布脚本检查；不构建应用、不部署 |
| 已映射的前端功能目录 | 后端核心检查、前端核心用例、该页面及关联页面用例、跨页面账务测试、类型检查及完整构建 |
| Java 贷款/资产/投资/账户/收支/汇率/报表/预算 | 整个资金联动组＋账本引擎、提醒、年度统计测试；全部前端测试 |
| Java 行情或 Python 行情适配器 | 行情、投资、报表接口测试及相关前端测试；Python 适配器测试 |
| 公共组件、API 客户端、鉴权/家庭权限、账本引擎、配置、迁移、依赖、CI 文件或未知路径 | 全量测试 |

前端采用显式模块联动表，不依赖不完整的动态 import 推断。比如投资页面关联总览、账户及资产目录下的投资联动测试；贷款关联资产、账户、总览。Java 业务改动保守地运行全部前端测试，因为接口消费者可能不在同名页面。

所有选测规则在 `scripts/ci_plan.py`。新模块默认全量，评估依赖后才能加入选测映射。不存在的测试、空清单或遗漏核心测试会直接失败，而不是通过。

### 核心检查

- 后端：金额精度、账本记账、事务重试、现金余额/回滚/重复扣款、换汇、登录、家庭权限、SPA 页面分发。
- 前端：API 错误处理、登录、写入后的刷新、换汇不确定结果重试、账户互转。
- 发布脚本及选测器测试每次运行；原发布安全脚本不变。

没有删除原有业务测试。关键路径之外的用例在关联改动、全量或夜间检查时运行。选测仍存在依赖映射遗漏风险，不能等同于完整回归，因此共享和不明改动始终全量。

## 如何避免漏掉前几次失败提交

- 推送/手动：比较当前提交与**同一分支最近成功的本工作流提交**，不是简单比较 `HEAD~1`。失败、取消、PR 或其他分支的运行不作为基线。
- PR：与目标分支和当前待测提交的合并基点比较。
- 改名按旧路径删除＋新路径新增处理，防止公共组件搬家后被误当成单模块改动。
- 测试文件被删除或改名时强制跑剩余全量测试；不自动恢复被删文件，也不能代替人工审查删除理由。
- API 无权限、历史缺失、找不到成功记录、基线不是祖先、输入不合法：全量。
- 基线查询最多读取最近 100 次成功记录；找不到可信基线就全量，不猜测。

## 全量检查

- 手动运行时勾选 `full_tests`，可单独完整检查而不部署 main。
- 工作流在默认分支每日北京时间 02:20 检查：与上次成功的夜间运行比较，有应用改动则全量，未变化或仅文档则跳过应用任务；首次没有基线则全量。GitHub 调度可能延迟。
- 数据库迁移、依赖、公共资金或权限代码变化，发布前直接全量，不能等夜间检查来兜底。

## 在 GitHub 查看结果

`plan` 的 Summary 和 `test-plan-<SHA>` 产物包含比较基线、改动路径、选测模式、确切测试清单和选择理由。未列入清单的无关用例本次不运行；`checks` 是统一完成门禁。

若仓库设置了必需状态检查，建议管理员将其指向 `checks`。旧 `build` 在纯文档场景会跳过，不适合作为唯一完整门禁。本轮不会自动修改 GitHub 分支保护设置。
